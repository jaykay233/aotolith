# Metal profiler captures (local)

Generated by `scripts/metal_profile_decode.py` under xctrace / MTL_CAPTURE_ENABLED.

| file | what |
| --- | --- |
| `decode_128.trace` | Instruments Metal System Trace, prompt=128 |
| `decode_4096.trace` | Instruments Metal System Trace, prompt=4096 |
| `decode_4096.gputrace` | Xcode Metal Debugger capture, 8 decode steps at capacity=4160 |

Open:
```bash
open -a "/Applications/Xcode-beta.app/Contents/Applications/Instruments.app" artifacts/metal_prof/decode_4096.trace
open -a "/Applications/Xcode-beta.app" artifacts/metal_prof/decode_4096.gputrace
```

Re-record:
```bash
xctrace record --template 'Metal System Trace' --time-limit 25s \
  --output /tmp/aoto_metal_prof/decode_4096.trace --launch -- \
  .venv/bin/python scripts/metal_profile_decode.py --prompt 4096 --steps 48

MTL_CAPTURE_ENABLED=1 .venv/bin/python scripts/metal_profile_decode.py \
  --prompt 4096 --steps 8 --warmups 1 \
  --gputrace /tmp/aoto_metal_prof/decode_4096.gputrace
```

## Inventory from the 4k gputrace

Kernel names baked with `4160` slots confirm decode walks the full capacity:

- `metal_decode_attention_14_2_4160_64_64_*` (24 layers × steps) - recorded
  before split-K; the current 4k path emits
  `metal_decode_attention_split_14_2_4168_64_64_16_*` plus its `_combine`
  sibling, and at 8k the split count is 16 over 8264 slots.
- `metal_rope_kv_cache_append_24_1_2_4160_64_*` (24 layers × steps)
- many `metal_*_gemv_transposed_1024_*` projections

Default Metal System Trace had **Shader Timeline: Disabled**, so the `.trace` export has GPU intervals without per-shader names. Use the `.gputrace` in Xcode’s Metal Debugger for encoder/shader detail.

## Follow-up: long-context levers (measured)

Decode on M5 Pro, `scripts/metal_profile_decode.py --steps 48`:

| prompt | before split-K | after split-K | `mlx_lm` |
| --- | --- | --- | --- |
| 128 | 4.59 ms (218 tok/s) | 4.93 ms (203 tok/s) | 4.63 ms (216 tok/s) |
| 1024 | 5.09 ms (196 tok/s) | 5.44 ms (184 tok/s) | 4.78 ms (209 tok/s) |
| 4096 | 6.93 ms (144 tok/s) | 6.94 ms (144 tok/s) | 5.13 ms (195 tok/s) |
| 8192 | 25.5 ms (39 tok/s) | 8.85 ms (113 tok/s) | 5.83 ms (172 tok/s) |

The 8k collapse was decode attention alone: one threadgroup per head scored the
whole window in 4k-key blocks, 0.93 ms per layer, 22 ms of a 25.5 ms step.
Split-K measures 0.021 ms per layer at 8224 keys, so attention is now under
half a millisecond of the 8k step and the remaining gap to `mlx_lm` is the
cache roll:

1. **24× `rope_kv_cache_append` rolls** - microbench 0.101 ms per launch at
   4168 slots (2.4 ms per step) and it grows with the window, which is the
   ~4 ms between the 128-token step and the 8k step. Host slice-assign of one
   slot is ~5-9× cheaper, but integrating it needs either:
   - IR-level `write_slot` + attention overlay (so `mx.compile` still sees real tensor edges), or
   - disabling compile for decode (ContextVar staging works, but loses the compile win and did not beat roll+compile end-to-end).

Note the roll's vector width does not move the end-to-end number. A wider vector
plus a four-way unrolled copy takes the launch from 0.118 to 0.101 ms at 4168
slots, which is 14% of 1.4 ms of a 6.9 ms step, and 4096 measures 6.94 ms
against 6.93 ms with the original width. An earlier revision of this file
reported 6.16 ms at 4096 and 7.86 ms at 8192; those were measured while a stride
mismatch left the kernel copying only the first wave of the window, so the
kernel was doing less work than the model needs.

Boolean pad keys now skip the Q·K dot in decode attention (left-pad prefix). That is cheap correctness-preserving bandwidth; it does not remove the roll launches.
